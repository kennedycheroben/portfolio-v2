## 1. Executive Stack Evaluation & Rendering Architecture

### 1.1 Comparison of Candidate Rendering & Routing Architectures

To achieve both high-fidelity interactive visual craft and deterministic search-engine crawlability (with social Open Graph scraping for WhatsApp, LinkedIn, Twitter/X, and Discord), four architectures were evaluated:

| Criterion | Model 1: Vite Client-Only SPA | Model 2: Custom Vite Prerender Script (`scripts/prerender.ts`) | Model 3: React Router v7 Static Pre-Rendering (RECOMMENDED) | Model 4: Full SSR Framework (Next.js App Router / TanStack Start) |
|---|---|---|---|---|
| **Social Crawlability & Meta Scraping** | **Unreliable.** Social bots (WhatsApp, LinkedIn, Twitter) do not execute JavaScript and parse blank shells. | Good, but fragile. Manual script must synchronize routes, HTML templates, and head tags. | **Deterministic & Native.** Pre-renders complete, crawlable HTML with route-specific `<title>`, `<meta>`, canonical URLs, and Open Graph tags. | **Deterministic.** Renders on-demand or at build time. |
| **Hydration Correctness** | N/A (Client-only). | **High Risk.** Differences between DOM generated by custom script and client bundle cause React 19 hydration mismatches. | **High Fidelity.** Shared component tree between pre-renderer and client minimizes markup divergence, verified via Playwright console audits. | Built-in, but requires complex server/client boundary management. |
| **Dynamic Routing (`/work/:slug`)** | Handled in client only. | Fragile. Requires manual slug array crawling. | **First-Class Manifest.** Static prerender manifest generates static HTML for all verified case study slugs at build time. | Handled via `generateStaticParams`. |
| **Operational Simplicity & Cost** | Lowest cost, but poor SEO. | High maintenance overhead for custom scripts. | **Zero Runtime Cost.** 100% static assets served from Vercel Edge CDN; serverless invocations triggered only on contact form or admin operations. | Serverless function invocations on public routes risk cold starts and compute limits. |
| **Admin Enclave Isolation** | Client-only route. | Client-only route. | **Isolated.** Admin (`/admin/*`) is code-split via `React.lazy()` into an authenticated client enclave; public pages remain zero-overhead static HTML. | Complex middleware and session caching required. |

### 1.2 Recommended Architecture: React Router v7 Static Pre-Rendering on Vite
- **Core Framework & Runtime:** **React 19** with **TypeScript** in strict mode.
- **Build Engine & Bundler:** **Vite 6+** leveraging official React Router v7 pre-rendering build target.
- **Rendering Lifecycle:**
  - **Build Time (SSG):** React Router v7 executes an export manifest containing all public static routes (`/`, `/about`, `/work`, `/contact`, `/resume`) and dynamic project routes (`/work/benchero`, `/work/whatsapp-vault`, `/work/jdm-kenya`, `/work/mediafusion`, `/work/unify-design`).
  - **Output:** Every public route produces an independent `index.html` containing complete semantic DOM, inline critical CSS, Open Graph metadata, and JSON-LD structured data.
  - **Client Hydration:** The browser loads pre-rendered HTML immediately. React 19 `hydrateRoot` hydrates the static DOM into an interactive single-page application.
- **Hydration Compatibility Assumptions & Engineering Constraints:**
  - **No Guarantee of Zero Hydration Mismatches:** Absolute elimination of hydration warnings cannot be guaranteed across arbitrary client environments due to browser extension DOM mutations (e.g. Grammarly, password managers, Google Translate, dark mode extensions), user-agent overrides, and dynamic client settings.
  - **Exact Compatibility Assumptions:**
    1. *Markup Parity:* The initial server-generated HTML and initial client-side render tree must be identical prior to user interactions in a clean browser environment.
    2. *Environment Isolation:* Build-time SSG executes in Node.js (fixed UTC timestamp, static headless environment). Browser runtime executes in user environment (local timezone, screen dimensions, window/document objects). All browser-dependent globals (`window`, `localStorage`, `navigator`, `Date.now()`) are forbidden during the initial synchronous render pass.
    3. *Two-Phase Rendering Contract:* Dynamic client-dependent features (e.g. system dark/light theme preference, Cloudflare Turnstile bot widget) render a static neutral skeleton or use a synchronous blocking inline script in `<head>` setting `<html class="dark">` with `suppressHydrationWarning` on the root tag, hydrating interactive state strictly inside `useEffect` post-mount.
- **Dynamic Route, 404 & Vercel Navigation Contract:**
  - **Static Pre-Render Manifest:** Case study slugs are statically enumerated at build time, outputting dedicated static HTML directories (`work/benchero/index.html`, etc.).
  - **Vercel Routing Configuration (`vercel.json`):** Configured with `cleanUrls: true` and route rewrites so `/work/:slug` serves `work/:slug/index.html` directly with HTTP 200 without trailing-slash redirect loops.
  - **404 Handling:** Requests for unmapped or non-existent slugs (e.g. `/work/non-existent`, `/missing-page`) do not fall back to an empty SPA client shell. Vercel serves the statically pre-rendered `404.html` with an HTTP 404 status code and an interactive home link.
- **Admin Data Isolation:** Public pre-rendered bundles import only static, verified project definitions from `src/content/`. Admin schemas, draft states, user credentials, and inquiry data are **strictly isolated** from public build manifests.

## 3. Contact Form: Distributed Rate Limiting & Secure Submission

### 3.1 Failure of In-Memory Rate Limiting in Serverless
In a serverless environment (such as Vercel Edge/Serverless Functions), instances scale horizontally and terminate unpredictably:
- **Stateless Containers:** In-memory variables (like a local JavaScript `Map`) exist only within an isolated container. Two concurrent requests often hit different lambdas, completely bypassing memory counters.
- **Cold Starts:** When an instance reboots, in-memory counters reset to zero, allowing malicious actors to flood endpoints by forcing cold restarts.
- **Conclusion:** Process-memory rate limiting is **insufficient**. A distributed, atomic, shared store is required.

### 3.2 Distributed Rate Limiting Evaluation & Failure Policy

| Rate Limiter Option | Cost | Operational Complexity | Latency | Failure Mode | Recommendation |
|---|---|---|---|---|---|
| **Upstash Redis (`@upstash/ratelimit`)** | Free tier (10k cmds/day) | Minimal. REST-based over HTTPS; zero connection pooling issues. | Sub-millisecond | Fail-over to Database RPC fallback with structured alert logging. | **RECOMMENDED PRIMARY** |
| **Supabase PostgreSQL Atomic RPC** | Included in Supabase project | Low. Dedicated table `rate_limits` with atomic stored procedure. | 20–40ms DB roundtrip | Catastrophic Double-Failure: Fail-Closed with HTTP 503 & direct email fallback. | **APPROVED FALLBACK** |
| **Cloudflare WAF / Turnstile Limits** | Free tier | Moderate. Requires routing full domain DNS through Cloudflare proxy. | Edge-level | Cloudflare-managed challenge / block. | Viable if DNS proxied |

#### Explicit Multi-Tiered Failure & Degradation Policy:
1. **Primary Rate Limiting (Upstash Redis):**
   - Implemented via `@upstash/ratelimit` with an atomic sliding window algorithm over HTTPS.
   - Timeout is capped at **500ms**.
2. **Secondary Fallback (Supabase PostgreSQL Atomic RPC):**
   - If Upstash is unreachable, errors, or times out (>500ms), the function immediately fails over to an internal atomic PostgreSQL stored procedure:
     `SELECT check_rate_limit(p_ip_hash := ip_hash, p_window_seconds := 600, p_max_requests := 3);`
   - Emits a structured operational warning log: `[WARN] RateLimiter: Upstash unreachable, fell back to PostgreSQL RPC`.
3. **Catastrophic Double-Failure Policy (Both Upstash & Supabase DB Unavailable):**
   - If *both* Upstash and Supabase PostgreSQL are unreachable:
   - **The endpoint FAILS CLOSED.**
   - Returns **HTTP 503 Service Unavailable** with header `Retry-After: 60`.
   - Response Body:
     ```json
     {
       "success": false,
       "error": "Our inquiry service is temporarily unavailable. Please wait a few moments and try again, or reach out through our alternative published contact channels.",
       "code": "SERVICE_UNAVAILABLE"
     }
     ```
   - **Architectural Rationale for Failing Closed:**
     - If the database is down, the inquiry cannot be safely stored in the database anyway.
     - Failing open during a database outage would allow attackers to hammer the serverless endpoint, consuming serverless compute resources and depleting third-party transactional email quotas (Resend free tier: 100 emails/day) without capturing leads.
     - Legitimate visitors receive an immediate, professional service status notification with explicit retry guidance, preventing misleading confirmations.

#### Calibrated Abuse Thresholds & Global Limit Reassessment:
- **Global Limit Reassessment:** The prior speculative limit of 60 submissions/minute across all IPs is **unjustified** for a personal portfolio website. 60 submissions/minute equates to 3,600 submissions/hour, which could exhaust the entire daily transactional email quota (100 emails/day) in under 100 seconds during a DDoS event.
- **Revised Global Threshold:** Reduced to **10 submissions per minute site-wide**. This comfortably accommodates legitimate burst spikes while capping maximum serverless and email exposure.
- **Multi-Tiered Limits:**
  - **Tier 1 (Per-IP Throttle):** Maximum **3 submissions per salted IP hash per 10-minute window**.
  - **Tier 2 (Global Endpoint Throttle):** Maximum **10 submissions per minute across all visitors**.
  - **Tier 3 (Per-Email Throttle):** Maximum **2 submissions per normalized recipient email address per hour**.

#### Protection of Legitimate Visitors:
- Legitimate visitors submit at most 1 inquiry every few minutes. Under normal conditions, legitimate users will never encounter rate limit rejections.
- If a legitimate visitor triggers a rate limit (e.g. sharing a high-traffic corporate NAT IP or university gateway):
  - The endpoint returns **HTTP 429 Too Many Requests** with header `Retry-After: 600`.
  - The frontend form UI displays a clear, helpful message: *"Submission limit reached for this network window. Please wait a few moments before trying again."*
- **Client Network Identity & Salted IP Derivation:**
  - Client IP is extracted strictly from trusted Vercel platform headers: `request.headers.get('x-vercel-ip')` or verified edge `x-forwarded-for`.
  - Plaintext IP addresses are never logged or stored. IP is hashed using a server-held secret salt:
    `ip_hash = HMAC-SHA256(client_ip, process.env.IP_HASH_SALT)`.

### 3.3 End-to-End Secure Submission Flow & Strict Persistence Contract

```
Visitor Browser                     Vercel Serverless (/api/contact)            Supabase DB            Email Provider
      |                                           |                                  |                       |
      | 1. POST { name, email, subject, message,  |                                  |                       |
      |          honeypot, turnstileToken }       |                                  |                       |
      |------------------------------------------>|                                  |                       |
      |                                           | 2. Zod Schema Validation         |                       |
      |                                           |    (Honeypot empty, length caps) |                       |
      |                                           | 3. Turnstile Secret Verify       |                       |
      |                                           | 4. Distributed Rate Limit Check  |                       |
      |                                           |--------------------------------->|                       |
      |                                           | 5. Server-Side Insert to contacts|                       |
      |                                           |    (Deny Anon; Server Secret)    |                       |
      |                                           |    [STRICT PERSISTENCE GATE]     |                       |
      |                                           |       /                   \      |                       |
      |                                           |  [FAILED]              [SUCCESS] |                       |
      |                                           |    |                       |     |                       |
      | 6a. HTTP 500/503 (NOT Saved)              |    |                       | 6b. Dispatch Alert          |
      |<------------------------------------------|----+                       |---------------------------->|
      |                                           |                            |   /                 \       |
      |                                           |                            |[FAIL]             [SUCCESS] |
      | 7. HTTP 200 (Saved Securely)              |                            |  |                    |     |
      |<------------------------------------------|----------------------------+--+                    |     |
```

#### Detailed Submission Pipeline & Failure Handling:
1. **Client Submission:** The browser POSTs JSON over HTTPS. Client-side code never communicates directly with the database.
2. **Server-Side Validation:** `api/contact.ts` validates payload via Zod (`name`, `email`, `subject`, `message`, empty `website` honeypot).
3. **Bot Challenge:** Turnstile token verified against `challenges.cloudflare.com`.
4. **Rate Limit Gate:** Upstash Redis with PostgreSQL RPC fallback. If double failure occurs, fail-closed with HTTP 503.
5. **Strict Persistence Gate (Database Insertion):**
   - Written to Supabase using `SUPABASE_SERVICE_ROLE_KEY` (held strictly in serverless environment variables).
   - **STRICT PERSISTENCE CONTRACT: Never claim a submission was received unless it was successfully persisted in the database.**
   - *If Database Write Fails:* The endpoint aborts execution, skips email dispatch entirely, and returns HTTP 500/503:
     ```json
     {
       "success": false,
       "error": "Your message could not be saved at this time. Please try again in a few moments.",
       "code": "PERSISTENCE_FAILED"
     }
     ```
6. **Transactional Email Notification & Decoupled Delivery:**
   - Triggered **only after database persistence is verified**.
   - *If Email Dispatch Succeeds:* Complete dual delivery accomplished.
   - *If Email Dispatch Fails:* The lead is **already safely recorded in PostgreSQL**. The client receives a successful response confirming persistence:
     ```json
     {
       "success": true,
       "message": "Your message has been received and stored securely.",
       "timestamp": 1728860000
     }
     ```
     The serverless handler logs an operational warning: `[WARN] ContactForm: Lead persisted (id: <lead_uuid>), but transactional email notification failed to dispatch. Queued for admin inbox review.`
7. **Privacy-Conscious Logging:**
   - Raw personal email addresses, visitor names, plaintext IP addresses, and message contents are **strictly prohibited from server logs**.
   - Operational logs record only: timestamp, request ID, HTTP status, error code, truncated salted IP hash (`ip_hash.substring(0, 12)`), and payload length.

## 7. Testing & Quality Assurance Plan

1. **Automated Playwright Hydration & Console Audit:**
   - Execute an automated Playwright test suite against production build previews across Chromium, Firefox, and WebKit.
   - Listen to `page.on('console', msg => ...)` and fail the test if React hydration mismatch errors occur (asserting clean logs matching regex `Hydration failed`, `Text content does not match`, or `did not match server-rendered HTML`).
2. **Direct Navigation & Deep-Link Refresh Tests:**
   - Verify direct browser navigation and hard refreshes to dynamic case study routes (`/work/benchero`, `/work/whatsapp-vault`, etc.) return pre-rendered HTML with HTTP 200, matching Open Graph meta tags in the raw response body, and mounting without flashing blank views.
3. **404 Route & Error Behavior Verification:**
   - Direct GET requests to unmapped URLs (e.g. `/work/non-existent`, `/missing-page`) must return pre-rendered `404.html` with an HTTP 404 status code from Vercel edge CDN, rather than falling back to an empty SPA client shell.
4. **Vercel Direct Navigation & Clean URLs Compatibility Tests:**
   - Validate that Vercel routes both `/work/benchero` and trailing-slash variants `/work/benchero/` consistently via `cleanUrls: true` without redirect loops or canonical mismatch warnings.
5. **View-Source Metadata & Social Scraper Verification:**
   - Fetch pre-rendered HTML via `curl -A "Twitterbot/1.0"` to verify `<title>`, Open Graph `<meta>`, canonical URLs, and JSON-LD schemas exist in raw response text before JavaScript execution.
6. **Rate-Limiter Multi-Tier & Double-Failure Resilience Tests:**
   - Fire 5 rapid requests from a single IP to `/api/contact` to verify the 4th request triggers HTTP 429 (`Retry-After: 600`).
   - Mock Upstash failure to verify seamless failover to PostgreSQL RPC.
   - Mock simultaneous Upstash and PostgreSQL failure to verify endpoint fails closed with HTTP 503 (`Retry-After: 60`) and returns user-friendly generic service-unavailable error payload.
7. **Security Regression & RLS Leak Tests:**
   - Verify unauthenticated and non-admin authenticated direct queries to Supabase `contacts` and `admin_users` tables return 0 rows.
